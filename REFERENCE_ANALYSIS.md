### 1. Mic_Loopback (pww1024) - `LoopbackService.kt`

**Actual code from repository:**

```kotlin

audioRecord = AudioRecord(
    MediaRecorder.AudioSource.MIC,    // Source: MIC (1) - basic, system adds processing

    AudioFormat.ENCODING_PCM_16BIT,

audioTrack = AudioTrack(
    AudioManager.STREAM_MUSIC,         // STREAM_MUSIC -> routes to current output device
    44100,
    AudioFormat.CHANNEL_OUT_MONO,
    AudioFormat.ENCODING_PCM_16BIT,
    bufferSize,
    AudioTrack.MODE_STREAM
)
```

Key characteristics:
- AudioSource: MIC (1) - system applies noise suppression + AGC
- Buffer: getMinBufferSize() * 2 - simple approach
- AudioTrack: deprecated constructor, STREAM_MUSIC
- NO AudioAttributes at all (no Builder API)
- NO NoiseSuppressor
- NO AudioManager mode change (stays MODE_NORMAL)
- NO audio focus request
- NO device routing or USB-C handling

Why it works on Samsung with USB-C: STREAM_MUSIC + MODE_NORMAL = Android routes to whatever
output is active (speaker/wired/USB-C/BT). No MODE_IN_COMMUNICATION means Samsung does NOT
switch to earpiece. The deprecated API bypasses some modern routing complexity that can fail.

**FullDuplex callback (FullDuplexPass.h):**

```cpp
// ONE callback for BOTH streams (output callback reads from input)
virtual oboe::DataCallbackResult onBothStreamsReady(
    const void *inputData, int numInputFrames,
    void *outputData, int numOutputFrames) {
    const float *inputFloats = static_cast<const float*>(inputData);
    float *outputFloats = static_cast<float*>(outputData);
    int32_t samplesPerFrame = getOutputStream()->getChannelCount();
    int32_t numInputSamples = numInputFrames * samplesPerFrame;
    int32_t numOutputSamples = numOutputFrames * samplesPerFrame;
    int32_t samplesToProcess = std::min(numInputSamples, numOutputSamples);
    for (int32_t i = 0; i < samplesToProcess; i++) {
        *outputFloats++ = *inputFloats++ * 0.95f;  // gain=0.95, add your processing here
    }
    // Silence-pad if input is shorter than output
    int32_t samplesLeft = numOutputSamples - numInputSamples;
    for (int32_t i = 0; i < samplesLeft; i++) { *outputFloats++ = 0.0f; }
    return oboe::DataCallbackResult::Continue;
}
```

**Disconnect handling:**

```cpp
void LiveEffectEngine::onErrorAfterClose(oboe::AudioStream* stream, oboe::Result error) {
    if (error == oboe::Result::ErrorDisconnected) {
        LOGI("Restarting AudioStream");
        openStreams();  // Auto-restart on USB-C plug/unplug
    }
}
```

Key characteristics:
- Output stream created FIRST, input sample rate matched = zero resampling
- TWO streams, ONE callback (FullDuplexStream coordinates them)
- Explicit deviceId for both streams = can target USB-C devices specifically
- AAudio default = full USB-C device enumeration support (requires Android 8+)
- EXCLUSIVE mode = lowest latency (auto-falls-back to SHARED)
- Auto-restart on ErrorDisconnected = handles USB-C plug/unplug gracefully
- CAVEAT (from README): "OpenSL ES does not allow setting recording or playback device"
  USB-C device selection requires AAudio. On Android < 8, no explicit USB-C routing possible.

## Key Lessons

### Lesson 1: AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE is WRONG for hearing aids

AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE is designed for:
- Alarm clock ringtones
- Incoming phone call ringtones
- GPS turn-by-turn navigation

It signals to Android: "I need ALL audio stopped immediately for an emergency."
On Samsung devices, this triggers phone-call audio routing rules, which can route
audio to the earpiece instead of the headphone/USB-C output.

For a long-running hearing aid service: use AUDIOFOCUS_GAIN (permanent focus).
Vatbub uses AUDIOFOCUS_GAIN deliberately after testing. The semantics:
- AUDIOFOCUS_GAIN = "I am the primary audio app" (music player behavior)
- AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE = "EMERGENCY - silence everything" (alarm/call behavior)

### Lesson 2: MODE_IN_COMMUNICATION causes Samsung to route to earpiece

Setting audioManager.mode = AudioManager.MODE_IN_COMMUNICATION tells Samsung HAL:
"We are in an active voice call." Samsung firmware responds by:
1. Routing output to the EARPIECE (small phone speaker) even with USB-C connected
2. This happens with both wired and USB-C headsets on affected Samsung models
3. Enabling voice call echo cancellation that modifies the audio path

Fix: NEVER set MODE_IN_COMMUNICATION for a hearing aid. Keep MODE_NORMAL always.
USAGE_MEDIA on AudioTrack + MODE_NORMAL = correct routing to connected output device.

### Lesson 3: STREAM_MUSIC / USAGE_MEDIA always routes to active output device

Both working references use the Music/Media audio path:
- Mic_Loopback: STREAM_MUSIC (deprecated constructor)
- vatbub: SL_ANDROID_STREAM_MEDIA

Android audio policy for STREAM_MUSIC/USAGE_MEDIA follows the active output:
- Phone speaker (default)
- Wired 3.5mm headset/headphones
- USB-C DAC adapter / digital headset
- Bluetooth A2DP (when connected)

Our app correctly uses USAGE_MEDIA on AudioTrack but uses USAGE_ACCESSIBILITY for audio focus.
Samsung's audio policy uses the focus attributes to determine routing intent.
This mismatch can confuse Samsung routing, causing it to apply accessibility routing rules.

### Lesson 4: USB-C on Samsung requires explicit setPreferredDevice()

Oboe LiveEffect explicitly supports deviceId for both input and output streams.
This is how you guarantee routing to a specific USB-C adapter DAC.

Our app detects TYPE_USB_HEADSET in isCompatibleDevice() but never calls
audioTrack.setPreferredDevice() with that device. On some Samsung models
(Galaxy S22+, S23+, S24 series), USB-C audio adapters don't auto-select
with USAGE_MEDIA + MODE_NORMAL alone. Explicit device selection is required.

Steps needed:
1. audioManager.getDevices(GET_DEVICES_OUTPUTS) -> find TYPE_USB_HEADSET
2. audioTrack.setPreferredDevice(usbHeadsetDevice) -> force USB-C output
3. audioRecord.setPreferredDevice(usbMicDevice) -> input from USB-C mic if present

### Lesson 5: UNPROCESSED AudioSource is ideal for hearing aids

Vatbub code shows explicit testing of three presets with two commented out:
```
// SL_ANDROID_RECORDING_PRESET_GENERIC,          <- tested and rejected
SL_ANDROID_RECORDING_PRESET_UNPROCESSED,         <- FINAL CHOICE
// SL_ANDROID_RECORDING_PRESET_VOICE_COMMUNICATION, <- tested and rejected
```

AudioSource values:
- MIC (1): Noise suppressor ON, AGC ON, beam-forming ON -> over-processed
- VOICE_RECOGNITION (6): Noise suppressor OFF, AGC OFF, beam-forming ON -> current hark-app
- CAMCORDER (5): Camera-optimized beam-forming
- UNPROCESSED (9): ALL processing OFF -> raw microphone signal

For a hearing aid, UNPROCESSED is ideal: users need the natural acoustic environment,
not a phone-call-optimized signal. AGC is especially harmful - it changes amplification
levels in ways the user cannot predict. Available API 24+ (Android 7+).

```kotlin
private fun updateAudioRouting() {
    val audioManager = getSystemService(AUDIO_SERVICE) as AudioManager
    // REMOVED: audioManager.mode = AudioManager.MODE_IN_COMMUNICATION
    // Reason: Causes Samsung to route output to earpiece instead of USB-C/headphone
    // USAGE_MEDIA + MODE_NORMAL correctly routes to connected output device

    if (preferExternalMic && Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
        val devices = audioManager.getDevices(AudioManager.GET_DEVICES_INPUTS)
        val btMic = devices.find {
            it.type == AudioDeviceInfo.TYPE_BLUETOOTH_SCO ||
            it.type == AudioDeviceInfo.TYPE_BLE_HEADSET
        }
        btMic?.let {
            HarkLog.i(TAG, "Setting communication device: ${it.productName}")
            audioManager.setCommunicationDevice(it)
        }
    }

    // Detect and store preferred output device for AudioTrack
    preferredOutputDevice = findPreferredOutputDevice(audioManager)
}

private fun findPreferredOutputDevice(audioManager: AudioManager): AudioDeviceInfo? {
    val outputs = audioManager.getDevices(AudioManager.GET_DEVICES_OUTPUTS)
    return outputs.firstOrNull { it.type == AudioDeviceInfo.TYPE_USB_HEADSET }
        ?: outputs.firstOrNull { it.type == AudioDeviceInfo.TYPE_WIRED_HEADSET }
        ?: outputs.firstOrNull { it.type == AudioDeviceInfo.TYPE_WIRED_HEADPHONES }
}
```

### Priority 4: Try UNPROCESSED AudioSource (AudioStreamManager.kt)

```kotlin
@SuppressLint("MissingPermission")
private fun createAudioRecord(channelConfig: Int, audioFormat: Int, bufferSize: Int,
                              preferredDevice: AudioDeviceInfo? = null): AudioRecord {
    // UNPROCESSED = raw mic signal, ideal for hearing aids (no noise suppression, no AGC)
    // Available API 24+ (Android 7.0 Nougat). Falls back to VOICE_RECOGNITION if unsupported.
    val audioSource = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.N) {
        MediaRecorder.AudioSource.UNPROCESSED
    } else {
        MediaRecorder.AudioSource.VOICE_RECOGNITION
    }

    val record = AudioRecord(audioSource, Constants.Audio.SAMPLE_RATE,
        channelConfig, audioFormat, bufferSize)

    if (record.state != AudioRecord.STATE_INITIALIZED) {
        Log.w(TAG, "UNPROCESSED source not supported, falling back to VOICE_RECOGNITION")
        record.release()
        return AudioRecord(MediaRecorder.AudioSource.VOICE_RECOGNITION,
            Constants.Audio.SAMPLE_RATE, channelConfig, audioFormat, bufferSize)
    }

    preferredDevice?.let {
        record.setPreferredDevice(it)
        Log.i(TAG, "AudioRecord.setPreferredDevice(${it.productName})")
    }
    return record
}
```

## The Samsung USB-C Failure Chain

When our app failed on Samsung with USB-C adapters:

```
Step 1: User plugs in USB-C headset
    Android detects TYPE_USB_HEADSET
    Our app calls audioManager.mode = MODE_IN_COMMUNICATION   <- BUG 1
    Samsung HAL: "VoIP call mode activated"
    Samsung routes output to EARPIECE (small phone speaker)
    Sound comes from phone speaker, not USB-C headset

Step 2: Audio focus request with AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE  <- BUG 2
    Samsung sees: "emergency audio request"
    Samsung audio policy applies phone-call routing rules
    Further reinforces earpiece routing
    Other audio apps pause completely (unnecessary)

Step 3: AudioFocus attrs use USAGE_ACCESSIBILITY, AudioTrack uses USAGE_MEDIA  <- BUG 3
    Inconsistency: focus policy = accessibility, playback = media
    Samsung routes different usages differently
    May apply screen-reader routing rules to focus management

Step 4: No setPreferredDevice() on AudioTrack  <- BUG 4
    On Samsung Galaxy S22/S23/S24 with USB-C adapters:
    USAGE_MEDIA alone is not enough to auto-select USB-C DAC
    System default may be built-in speaker or Bluetooth
    Result: audio goes to wrong output device
```

Fix priority: BUG 1 (MODE_NORMAL) and BUG 2 (AUDIOFOCUS_GAIN) are the
highest impact changes for Samsung USB-C routing. Apply both together.
